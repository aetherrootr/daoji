# 初始 Rust 架构

> 本文档是非权威的简体中文翻译。请参阅[英文原文](../../../design/0001-initial-rust-architecture.md)；如有语义冲突，以英文原文为准。

状态：已验收 0

文档类型：架构决策

决策负责人：项目所有者

批准：项目所有者于 2026-08-02 在来源对话中批准 Rust 用于初始脚手架，并推迟所有
额外工具链决策。

## 背景

Daoji 最初是一个文档和元数据验证器，但后续自我开发级别将协调 AI 智能体、执行
工具并保留证据。因此，工程脚手架既要支持较小的首次实施，也要支持未来的智能体
执行框架。来源请求要求采用严格的自动化测试和代码检查，因为 AI 智能体将生成
实施变更。

同类规范工具采用了不同的技术栈。GitHub Spec Kit 使用 Python、Ruff 和 pytest。
OpenSpec 使用 TypeScript、ESLint 和 Vitest。相似的智能体执行框架为初始核心提供了
更有价值的参考：OpenAI Codex 和 Goose 使用 Rust 实现进程和协议逻辑。这些项目也
说明额外工具链会增加构建、依赖、接口和测试成本，因此应由具体产品需求驱动。

## 决策

Daoji 的初始实施将使用 Rust：

- Rust 负责领域模型、文档验证、政策、协调、供应商中立协议、进程控制和命令行
  界面。
- 初始脚手架包含一个 Rust 二进制 crate。只有经过验证的组件边界才能证明拆分
  workspace 的必要性。
- 本决策不选择用户界面架构，也不选择额外的语言、运行时、软件包管理器或构建系统。
- 只有已验收需求和设计证明其行为、边界、维护成本及验证方式合理时，未来变更才能
  添加其它工具链。

初始工具链采用 Rust 2024，最低支持 Rust 版本为 1.85.1。脚手架没有运行时依赖项。
后续依赖项必须经过 Rust 工程政策规定的评审。

## 优点

- Rust 通过 `rustc`、`cargo`、`rustfmt`、Clippy、内置测试框架和文档测试提供约定
  明确且现成的验证套件。成熟的 Cargo 工具还覆盖代码覆盖率、安全公告、许可证和
  依赖政策。
- 类型系统、编译器、`unsafe_code = "forbid"` 和严格 Clippy 规则可以在评审前将
  已定义类别的缺陷转换为机械检查失败。
- 这些现有检查让仓库可以保持 Rust 工程政策简洁，而无需重新陈述大量工具无法执行的
  规则。
- Rust 可以生成经过优化且无需用户另行安装语言运行时的独立原生二进制文件。功能
  代码的性能声明仍须依据已验收需求进行基准测试。
- 推迟其它工具链可以避免在对应需求出现前引入额外锁文件、重复检查和不成熟接口。

## 缺点

- Rust 源代码和基于 Cargo 的质量工具需要编译，这会增加本地及 CI 时间和存储成本。
  项目尚未测量这项成本。
- 分发原生二进制文件需要针对每个受支持的操作系统和处理器目标进行构建与测试。
- 编译器和代码检查成功不能证明需求正确。测试、保留证据和人员评审仍然必不可少。
- 固定的最低工具链需要有计划地升级并进行兼容性测试。

## 未选择的替代方案

**仅使用 Python：** 此方案可以实施 Level 1，并与 Spec Kit 一致。Python 是一个
可行方案，项目未因其存在固有安全缺陷而排除它。要满足本变更选定的门禁，项目需要
分别选择和协调格式化、代码检查、类型检查、测试、覆盖率、审计、许可证、打包和
运行时政策。初始脚手架改为选择 Rust 约定明确且以 Cargo 为中心的检查和独立二进制
文件。

**仅使用 TypeScript：** 此方案与 OpenSpec 一致，并拥有强大的 Markdown 和 UI 库。
TypeScript 也是可行方案。初始脚手架没有选择它，因为已验收决策偏好标准化的 Rust
验证套件，以及无需另行安装语言运行时的原生二进制文件。本决策不评估 TypeScript
是否适合尚未规定的未来组件。

**立即使用多套工具链：** 此方案可以提前验证集成边界。项目未选择该方案，因为没有
已验收需求定义需要其它工具链的能力。现在添加工具链需要增加政策、锁文件、验证命令
和集成测试，却不会增加已验收行为。

## 影响

首次功能变更应将解析和验证保留在 Rust 中。本决策不偏好任何用于未规定未来组件的
语言或框架。添加其它工具链的提案必须在当时比较继续使用 Rust、添加该工具链和其它
适用替代方案。
