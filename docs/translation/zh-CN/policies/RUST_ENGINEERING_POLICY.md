# Rust 工程政策

> 本文档是非权威的简体中文翻译。请参阅[英文原文](../../../policies/RUST_ENGINEERING_POLICY.md)；如有语义冲突，以英文原文为准。

文档类型：工程政策

范围：Daoji 仓库中的所有 Rust 源代码、测试、构建逻辑、依赖项和 CI 自动化。

## 工具链和代码

仓库必须声明 Rust edition 和最低支持 Rust 版本。CI 和本地验证必须使用已提交的
锁文件。源代码必须使用 `rustfmt`。所有目标和功能上的 Clippy 警告都必须导致验证
失败。除非权威设计和政策批准的例外定义安全论证及独立评审，否则 crate 必须禁止
不安全代码。

除非本政策的例外流程明确允许，生产代码不得使用 `unwrap`、`expect`、`panic!`、
`todo!` 或 `unimplemented!`。测试可以使用断言，但应返回或比较错误，不得隐藏失败
上下文。公共项必须有文档。

## 代码检查例外

代码检查例外是明确的工程记录，而不是为了方便而使用的抑制方式。例外不得在
`Cargo.toml` 中降低或禁用 workspace 代码检查。在提案开发期间，请把请求的例外连同
原因应用于范围最小的项或模块，例如：

```rust
#[allow(clippy::todo, reason = "EXC-001: candidate prototype boundary")]
fn provisional_path() {
    todo!("EXC-001")
}
```

当前变更条目必须在合并前定义该例外。每条例外记录必须包含：

- 唯一标识符，以及被抑制的代码检查或规则。
- 范围内的确切文件、项、目标和配置。
- 当前不适合采用合规实施的原因。
- 已考虑的替代方案，包括返回类型化错误或省略未完成代码。
- 仓库评审证据、残余风险和受影响需求。
- 限制例外路径何时可以执行的测试或其它检查。
- 到期日期、里程碑或可客观测试的移除条件。

`todo!` 或 `unimplemented!` 例外还必须说明权威原型计划或同一提案中经过验证的候选
原型计划为何需要可执行占位程序。受此类例外覆盖的代码仍然未完成，不能满足实施任务的完成标准。除非权威政策明确
允许发布并定义其失败行为，否则该代码不得进入生产版本。智能体必须在工作结果和
实施记录中报告每一处使用。

只有当内部政策验证确认权威政策允许请求的例外，并且仓库治理报告 PR head Git commit 具有
全部必需评审和强制检查时，请求的例外才会成为已批准合并的例外。

## 依赖项和供应链

每个依赖项都必须满足控制性的权威需求或设计决策，或者同一变更提案中经过验证的候选
需求或设计决策。优先使用标准库和现有依赖项。版本必须锁定。`cargo audit` 不得报告警告。
`cargo deny` 必须拒绝未经批准的许可证、注册表、
Git 来源、通配符要求、已撤回 crate 和重复依赖版本。CI action 必须固定到完整的
提交哈希。

自动更新可以提出依赖项和 action 变更，但不能绕过正常评审和验证过程。

## 测试

每项行为变更必须在最窄的有效层级包含确定性测试。除非控制性的权威验证计划或同一
提案中经过验证的候选验证计划定义隔离和清理，否则测试不得依赖网络访问、机密信息、实际
时间或共享可变状态。不得通过重试失败的强制检查来隐藏非确定性。

初始脚手架仅包含进程入口点，因此要求 100% 行覆盖率。功能变更在降低该值前，必须
通过权威政策定义并说明其覆盖率阈值。变更阈值的提案在政策变更合并前必须继续通过
权威阈值。覆盖率不能代替面向行为的断言或评审。

CI 必须运行格式化、Clippy、测试、文档、release 构建、覆盖率、公告、许可证、来源
和依赖政策检查。测试必须在 Linux、macOS 和 Windows 上运行。本地检查可以缩小范围
以提供快速反馈，但所有 CI 检查都是合并的强制条件。

## 接口和生成资产

根据当前权威架构，Rust 是核心领域和验证行为的权威来源。本政策不选择未来组件的工具链。
如果权威设计添加其它工具链，该设计及其政策必须定义执行权限、接口权威性、兼容性
检查和生成资产规则。提案可以添加不执行的工具链资产，但在权威设计和政策允许执行前，
不得执行新工具链。权威 CLI 需求或同一提案中经过验证的候选需求定义相关接口时，项目必须提供人类可读的失败消息和稳定的机器可读输出。机器可读输出格式可以定义模式版本；本政策文档没有人工版本。

## 安全和运维

将仓库文档和智能体输出视为不可信输入。新增文件系统、进程、网络、机密信息或
供应商访问前，必须有权威威胁模型和明确测试。初始脚手架除了进程启动和退出外
不执行 I/O。它不创建部署、迁移、数据保留、监控或发布行为；相关需求使这些类别
适用前，推迟制定其政策。

## 执行

[工程脚手架变更](../changes/0001-engineering-scaffold.md)中的命令和 CI 工作流执行
本政策。内部政策验证必须确认权威政策允许例外且例外记录完整。例外必须明确受影响
路径。仓库治理根据实际差异确定控制性受影响路径，并且必须报告 PR head Git commit 具有有效的
必需路径 OWNER 评审和强制检查。适用的变更条目必须说明原因、范围、到期条件和残余风险。

## 变更说明

- 建立初始 Rust 工程规则。
- 定义限定范围的代码检查例外记录，以及对可执行占位程序的附加控制。
- 将例外评审和合并授权委托给仓库治理。

Git 历史标识引入每项变更的确切修订。
