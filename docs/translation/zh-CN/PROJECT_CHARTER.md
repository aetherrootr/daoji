# Daoji 项目章程

> 本文是非权威的简体中文翻译。请参阅[英文原文](../../PROJECT_CHARTER.md)；如有语义冲突，以英文原文为准。

文档类型：项目章程

长度评估：本章程将初始项目规则保留在一起，以便读者评估其优先级和一致性。读者应该使用章节标题进行导航，并通过链接标准查阅操作细节。

强制使用：项目工作必须遵循权威分支上此路径中的章程。替换章程必须使用类型化取代关系并经过授权合并。

## 目的

本章程规定了 Daoji。Daoji 是一个协调 AI 智能体并将项目规则应用于 AI 辅助软件工程的工具。Daoji 必须使用文档定义的软件开发（Document-Defined Software Development，DDSD）来创建和更改大型软件系统。DDSD 是一种由权威文档规定和控制软件工作的流程。

Daoji 不是 AI 智能体。规定的工程工具必须调用并协调 AI 智能体。它必须向每个智能体提供来自权威项目记录和当前变更提案的上下文，并区分候选资产和权威资产。它还必须向每个智能体提供一项具有明确范围、约束和完成标准的任务。Daoji 必须在变更提案中记录由此产生的更改和验证证据。

在 DDSD 中，每份文档都有类型、范围、稳定身份以及指向相关工程资产的类型化链接。Git commit 标识确切仓库快照，需要时由 Git blob 标识确切文件修订。只有机器可读格式可以具有模式版本。适用时，生命周期文档必须包含或链接到验收标准。文档描述工作并控制项目决策。每项软件变更都必须链接到要求实施该变更的决策。开发分支上的工作始终是变更提案。当提案具有必需的路径 OWNER 评审和强制检查时，获得授权的执行者可以将其合并到受保护的权威分支。该合并以原子方式将候选仓库快照纳入权威项目记录。

本章程是 Daoji 优先级最高的项目文档。它定义项目的目的、价值观和规则。所有其他项目资产都必须与本章程一致。除非本章程或权威项目政策纳入外部政策、标准和工程实践，否则它们不直接控制项目。

本章程使用以下术语：

- **工程资产：** 项目创建或维护的文档、软件项或记录。
- **权威文档：** 权威分支中适用路径上的文档，其类型和范围规定项目的需求、规则或决策。
- **权威项目记录：** 项目用作决策正式依据、受版本控制的项目信息集合。
- **权威分支：** 受保护的仓库分支；其已合并内容构成权威项目记录。
- **权威快照：** 由 Git commit 标识的确切权威项目记录。
- **变更提案：** 开发分支及其拉取请求中相互关联的文档、软件变更、记录和证据。变更条目保存提案的工作流状态。
- **候选资产：** 变更提案中尚未合并的工程资产。通过适用验证后，候选资产可以控制该提案内的工作，但不具有权威性。
- **已批准：** 仓库治理系统报告为对变更提案 PR head Git commit 有效的评审批准。
- **仓库治理：** 控制项目能否合并变更提案的路径所有权、必需评审、强制检查、分支保护、合并授权及相关仓库规则。
- **AI 智能体提供商：** 提供 AI 智能体访问能力的服务或软件系统。

文档权威性由系统推导，不作为文档元数据存储。获得授权的合并把候选资产的路径放入权威分支后，该资产成为权威资产。Git 历史记录修订；类型化关系记录语义派生、取代和历史保留。

## 问题陈述

AI 智能体可以快速生成有用的代码。但是，在大型项目中，如果工作流在项目创建权威文档之前就向 AI 智能体分配工作，会产生以下问题：

- 临时提示词是项目目标的唯一记录。
- 需求、设计决策和实现细节混杂在一起。
- 不同智能体作出不兼容的假设。
- 局部更改违反适用于整个系统的约束。
- 生成的代码看似完整，却没有经过充分验证。
- 交互结束后，决策的理由会丢失。
- 由于项目没有定义哪些信息控制决策，代码和文档会变得不一致。

Daoji 必须保留项目上下文。Daoji 必须分配范围明确的工作。Daoji 必须记录决策之间的链接。没有留存证据时，Daoji 不得报告生命周期或验证已经就绪。只有获得授权的合并才能采用工作。Daoji 不得假设一个模型或智能体可以一次理解整个系统。

## 目标

1. 将人的目标转化为可供人评审的明确工程资产。
2. 记录需求、设计、政策、计划、代码、测试、构建结果和已发布软件行为之间的链接。
3. 向每个 AI 智能体提供所需的最少上下文，以及一项范围明确定义的任务。
4. 当自动检查可行时，将其用于项目规则。当自动检查不可行时，要求指定一名评审者。
5. 在矛盾信息、缺失决策、过时文档和缺乏证据的陈述导致实现缺陷之前，检测出这些问题。
6. 同时适用于新系统的开发和大型现有系统的受控现代化改造。
7. 确保核心概念不依赖特定模型、智能体、编程语言、构建系统或源代码托管提供商。
8. 对每一项工作已完成的声明，都要求保留验证证据。
9. 使用 Daoji 自身的规则和工作流控制其开发。
10. 像对软件资产一样，对设计和文档应用版本控制、评审、校验和由仓库治理的路径所有权。
11. 对人和软件智能体使用同一份权威文档。
12. 使用准确、简单、易于翻译的英语，使来自不同语言和文化背景的读者都能理解项目。

## 非目标

以下能力不在 Daoji 的范围内：

- Daoji 不会将人排除在产品或架构决策之外。
- Daoji 不会仅通过生成文档来保证正确性。
- Daoji 不充当 AI 智能体、通用代码编辑器或聊天界面。
- Daoji 不规定一种软件架构或开发方法。
- Daoji 不隐藏不确定性，也不自动解决重要选择，包括这些选择的利弊。
- Daoji 不接受未经项目定义的验证的生成代码。
- Daoji 不要求所有文档都是自然语言散文。

当结构化数据、图表、模式、决策记录、可执行检查和测试规范位于权威分支的适用路径，且其类型和范围赋予相应语义作用时，它们可以控制工作。

## 基本原则

以下原则控制 Daoji 开发。

### 文档和智能体的职责

智能体可以分析、提议、实现和验证。它们不得暗中创建项目级需求或政策。如果权威记录和当前提案中已记录的决策都没有提供所需决策，智能体必须请求该决策。智能体不得作出并应用未记录的项目级决策。

### 明确的文档优先级

受项目规则约束的每项工程资产都必须具有明确的类型和范围。如果两项资产发生冲突，系统必须报告冲突并使用已记录的优先级规则。系统不得在未应用该规则的情况下选择文本。

### 资产可追溯性

开发模型展示了一个顺序，但项目可以返回较早阶段。需求可能要求更改设计。验证可能表明需求不正确。实现工作可能表明计划不正确。Daoji 必须记录这些更改的类型化链接。链接需要确切仓库修订时，必须使用 Git commit 或 blob 标识符。

### 智能体任务范围和完成标准

智能体任务必须明确其输入、许可范围、约束、预期输出和完成标准。实现计划是这些任务规范的集合，而不是一组无结构的提示词列表。

### 验证证据

“测试应该通过”不是证据。项目必须保留命令、环境信息、结果、失败、例外和相关工程记录。这些信息必须表明工作是否满足验收标准。

### 行为变更的权威文档

行为变更从识别定义和允许当前行为的文档开始。如果代码发生更改，但适用的需求、设计、政策、计划或验证标准仍然过时，则该变更尚未完成。

### 由仓库治理控制的采用

Daoji 不维护独立的项目审批角色系统。仓库治理系统根据实际仓库差异中的路径确定必需评审者、验证强制检查、保护权威分支，并确定谁可以合并。计划和记录中声明的路径用于规划和可追溯性，但不控制评审者选择。评审批准必须适用于 PR head Git commit。仓库规则决定后续 commit 何时撤销批准或使批准失效。

开发分支上的所有文档、软件和记录在合并前均为候选资产。变更条目工作流状态、AI 结论、评论或本地转换都不能使候选资产获得权威性。所有必需的路径 OWNER 评审、成功的强制检查和获得授权的合并共同构成采用决策。只有仓库治理规则明确允许时，自动化才可以评审、检查或合并。

Daoji 必须向人员和工作流暴露仓库治理状态，不得复制或覆盖仓库的最终合并授权。仓库适配器必须将评审和检查状态绑定到仓库、目标分支、拉取请求及 PR head Git commit。

### 权威项目记录

受保护权威分支中已合并的内容最初是权威项目记录。开发分支、拉取请求、聊天历史和模型记忆可以协助工作，但仍属于候选内容或资料性信息，在合并前不能控制权威项目决策。

### 软件资产所需的文档

智能体在开发分支上创建软件资产之前，必须有一份权威文档或同一变更提案中的候选文档要求或允许该资产。软件资产包括源代码、测试、模式、配置、构建逻辑、部署定义、生成的输出和自动化。候选文档可以证明同一提案中的候选实施工作合理，但在合并前不能扩大权限、授予机密访问权或覆盖权威政策。

项目不需要为每个文件编写一份文档。每项软件资产都必须链接到一份文档，该文档说明为什么需要该资产、适用哪些约束，以及强制检查如何确定是否已达到合并就绪状态。同一变更提案中的原型计划可以允许原型先于最终设计。该计划必须说明要研究的问题、范围、生命周期，以及删除原型或将其纳入系统的标准。

### 必需的文档和设计

文档和设计是软件项目的必需组成部分。项目必须根据受影响路径、每份文档或设计的类型、范围和关系，对其应用版本控制、评审、校验和仓库路径治理。实现工作必须包括所需的文档和设计。在项目完成实现之前，项目必须创建这些文档和设计。

如果权威文档和当前变更提案都没有定义用户可见的能力，项目不得合并该能力。如果已合并实现与权威文档不一致，项目必须记录一个缺陷。项目必须通过已记录的变更流程解决冲突。

### 文档治理

[Daoji 文档标准](standards/DOCUMENTATION_STANDARD.md)定义所有项目维护文档必须遵守的结构、长度预算、渐进式披露、文档图、仓库地图、语言、评审和维护规则。项目工作必须遵循该标准。

该标准必须为人和智能体保留一个控制性来源，为权威文档使用准确且可翻译的英语，并要求文档保持可从根目录文档地图到达。如果文档标准与本章程冲突，以本章程为准。

## 生命周期阶段和退出条件

Daoji 开发包含以下阶段：

1. 意图
2. 需求
3. 设计
4. 工程政策
5. 实现计划
6. 验证计划
7. AI 生成的代码
8. 实现记录
9. 构建和验证
10. 验证记录
11. 变更摘要
12. 可运行软件

每项软件变更都必须将其来源请求追溯到候选或权威的意图、需求、设计、适用工程政策、实现和验证计划、实现和验证记录以及变更摘要。当项目无法安全保留来源请求时，必须记录原因。对于小型变更，项目可以合并资产，但不得省略必需的决策、证据、评审、可追溯性或仓库治理。

实施开始前，变更提案必须包含控制性文档，并通过生命周期标准定义的实施前检查。这些文档在合并前仍是候选资产。项目必须在合并前完成实现记录、验证记录和变更摘要。合并会使用候选仓库快照以原子方式更新权威分支；评审、检查和合并元数据继续作为链接的治理证据。

[Daoji 开发生命周期标准](standards/DEVELOPMENT_LIFECYCLE_STANDARD.md)定义工作流、生命周期文档裁剪规则、工程政策评估、阶段要求、验证层和退出条件。项目工作必须遵循该标准和[文档标准](standards/DOCUMENTATION_STANDARD.md)。

## 初始工程资产模型

“目的”一节定义了**工程资产**这一术语。工程资产定义、实现或验证软件系统，为软件系统的运行提供信息，或记录软件系统的历史。

Daoji 必须至少表示以下工程资产类别：

| 工程资产 | 必需信息 |
| --- | --- |
| 意图 | 预期结果的理由和对该结果的描述。 |
| 需求 | 系统必须满足的可观察条件。 |
| 设计 | 系统如何满足需求。 |
| 决策记录 | 一项重要决策、该决策的理由，以及项目考虑过的替代方案。 |
| 工程政策 | 适用于一项或多项智能体任务的规则。 |
| 实现计划 | 具有明确范围、说明智能体如何实现设计的有序智能体任务。 |
| 验证计划 | 用于测试和验证的方法、命令、环境、输入和预期结果。 |
| 工作结果 | 智能体所做的更改、产生的输出和发现的信息。 |
| 实现记录 | 已实现的更改、受影响的组件，以及对控制性的权威或候选设计和计划的偏离。 |
| 验证记录 | 表明工作是否满足适用验收标准的已记录结果。 |
| 变更摘要 | 适合用作 PR 描述的简明列表，包括更改、实现说明、验证结果、风险和未解决工作。 |
| 发布记录 | 已发布的软件版本及其支持的运行环境。 |

后续设计文档必须定义机器可读格式及其元数据模式。模式版本只适用于机器可读格式。每项工程资产都必须具有永久标识符、文档或资产类型、范围以及指向相关资产的类型化链接。维护与评审责任由仓库路径治理推导。只有变更条目保存变更提案的工作流状态。Git 历史提供修订历史，Git commit 或 blob 标识符标识确切修订。文档标准定义临时文档元数据和链接规则。

在项目定义标识符和元数据模式之前，每项工程资产都必须具有仓库路径或其他稳定位置。每份文档都必须说明其文档类型，并明确其目的和范围。文档可以使用仓库路径和章节名称作为临时链接。

对于每项需求，项目应该维护一个权威来源。替换必须使用类型化的 `supersedes` 和 `superseded-by` 关系。项目可以删除被替换文档，或通过类型化历史关系保留它。

设计细节必须随风险和未解决问题的增加而增加。开发生命周期标准定义何时变更需要单独的设计文档，以及何时实现计划可以包含简短的设计记录。

## 临时文档优先顺序

在权威分支包含完整的文档优先级规则之前，系统必须报告语义冲突，并使用以下优先顺序解决冲突。操作权限只使用由目标分支 Git commit 标识的权威快照。合并验证使用合并后的候选快照，包括候选新增、替换和删除：

1. 被评估快照中的 Daoji 项目章程
2. 被评估快照中的意图和需求
3. 被评估快照中的设计决策
4. 被评估快照中的项目标准和适用工程政策
5. 被评估快照中的实现计划
6. 智能体指令和工作结果
7. 生成的实现细节

同一优先级资产之间未解决的冲突会阻止生命周期就绪和合并。候选资产不能放宽合并前工作所适用的权威权限或安全约束。

尽管优先顺序不包含证据，验证证据仍然重要。证据表明工作是否满足适用的需求和验收标准。证据本身不会更改这些需求。

## Daoji 自我开发

Daoji 应该逐步使用自己的工作流来开发自身。以下级别定义了实现该能力的进展。

### 级别 0：手工文档

人创建并评审章程以及根据章程需求创建的文档。通用工具和智能体可以提供协助，但 Daoji 没有可执行的实现。

### 级别 1：文档校验

一个最小工具校验 Daoji 仓库的工程资产结构、类型、标识符、类型化链接、变更条目工作流状态和基本政策规则。

### 级别 2：计划和任务创建

Daoji 根据权威资产和当前变更提案创建范围明确的智能体任务。Daoji 生成不依赖单一 AI 智能体提供商的任务规范。仓库治理控制结果变更的最终采用。

### 级别 3：协调执行

Daoji 调用一个或多个 AI 智能体接口。Daoji 限制每个智能体的上下文和任务范围、收集结果，并运行仓库中定义的验证命令。

### 级别 4：由 Daoji 控制的开发

Daoji 使用自己的工作流进行常规开发。每项 Daoji 变更都链接其意图、需求、设计、实现、验证和发布记录。PR head Git commit 必须具有有效的必需路径 OWNER 评审和强制检查，之后获得授权的合并才能更新权威分支。

Daoji 不得是验证 Daoji 的唯一系统。Daoji 自身的检查结果不足以证明 Daoji 正确。必须由人或独立工具评审初始实现组件、模式、政策变更和验证机制。评审量必须随风险增加。

## 初始工程政策

在实现特定政策出现之前，适用以下项目规则：

1. 不要仅仅为了开始编码而选择技术。必须由权威需求或当前变更提案中的需求和设计决策来证明选择合理。
2. 将需求与示例和说明性文本分开。
3. 项目定义标识符方案后，为每项工程资产提供永久标识符。
4. 记录不确定性、缺失信息和未解决的决策。不要把模型生成的假设表示为权威项目决策。
5. 优先采用对相同输入产生相同结果且可供评审者检查的协调和校验流程。
6. 在模型输出通过相关检查之前，将该输出视为不受信任的输入。
7. 除非权威设计和政策要求访问机密信息并规定该访问的控制措施，否则绝不向智能体暴露机密信息。
8. 核心模型不得依赖单一 AI 智能体提供商。将提供商特定行为放在单独的提供商接口中。
9. 定义每种失败条件及其恢复程序。智能体工作仍未完成时，不要把变更提案工作流标记为完成。
10. 当实现行为发生更改时，同一项拟议变更必须包含所需的文档和验证更新。

[文档标准](standards/DOCUMENTATION_STANDARD.md)控制文档创建、写作、链接、评审、维护和缺陷处理。

这些初始政策并未构成完整的实现政策集合。[开发生命周期标准](standards/DEVELOPMENT_LIFECYCLE_STANDARD.md#当前工程政策缺口)记录已知缺口，并定义每项变更如何检查政策完整性。

## 第一个文档周期

第一个文档周期应该生成以下工程资产：

1. 一份关于第一个里程碑的意图文档，在该里程碑中，Daoji 帮助开发 Daoji。
2. 级别 1 文档校验的功能需求和质量需求。
3. 工程资产、类型化链接、变更提案工作流转换和证据的领域模型。
4. 仓库布局、文档格式、校验和初始命令行界面的架构决策。
5. 项目工程政策，用于弥补适用于所选技术、架构、实现和验证范围的已知缺口。
6. 一份实现计划，其中包含智能体任务和完成标准，并链接到每项需求的验收标准。
7. 一份验证计划，定义项目如何验证每项需求和验收标准。
8. 项目仅在完成第 1 至第 7 项之后创建的生产代码。
9. 一份描述已实现结果的实现记录。
10. 一份包含实际命令、环境和结果的验证记录。
11. 一份适合直接用作 PR 描述的变更摘要。

## 开放问题

以下问题有意保持未解决状态：

- 文档的哪些部分应该是结构化数据，哪些部分应该是散文？
- 应使用哪些类型化关系词汇和验证规则表示优先级、取代、派生和历史保留？
- 最小且实用的级别 1 校验器是什么？
- Daoji 应该如何跨不同代码托管提供商表示仓库评审、检查和合并状态？
- 项目应该如何保留证据，同时避免仓库变得过大而不便正常使用？
- 当代码是软件设计的唯一记录时，Daoji 应该如何开始管理现有仓库？
- 哪种智能体接口能让 Daoji 使用不同的 AI 智能体提供商，同时避免将所有智能体限制为能力最弱的提供商所具备的功能？
- Daoji 应该如何报告并解决相互冲突的需求和政策？

后续需求和设计阶段必须处理这些问题。在没有明确、已记录的决策时，实现不得擅自回答这些问题。

## 资料性参考文献

项目在编写本章程时使用了以下来源。这些来源不控制 Daoji。只有权威 Daoji 工程资产中的需求才适用于项目。

- [Claude 宪法](https://www.anthropic.com/constitution)，用于采用明确透明的文档来陈述价值观、优先级和冲突解决规则。
- [文档驱动开发](https://gist.github.com/zsup/9434452)，用于在实现之前于文档中定义能力，并保持文档、测试和软件的一致性及版本化。
- [《Software Engineering at Google》：文档](https://abseil.io/resources/swe-book/html/ch10.html)，用于将版本控制和评审流程应用于文档、为明确声明的受众写作，以及维护权威文档。
- [Google 的设计文档](https://www.industrialempathy.com/posts/design-docs-at-google/)，用于在实现之前记录设计上下文、目标、非目标、决策、替代方案、相互竞争的利弊，以及适用于多个系统组件的关注事项。
- ATA iSpec 2200，因其采用结构化方法处理技术信息。
- ASD 简化技术英语，因其使用受控语言来提高翻译过程中的清晰度、一致性和准确性。
