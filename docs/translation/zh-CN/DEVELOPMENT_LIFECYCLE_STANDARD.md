# Daoji 开发生命周期标准

> 本文档是非权威的简体中文翻译。请参阅[英文原文](../../DEVELOPMENT_LIFECYCLE_STANDARD.md)；如有语义冲突，以英文原文为准。

状态：生效草案 0

文档类型：开发标准

长度评估：生命周期阶段保留在一起，因为后续阶段依赖早期阶段的退出条件。读者应该从变更流程开始，并通过链接进入当前工作所需的阶段。

强制使用：[Daoji 项目章程](PROJECT_CHARTER.md)要求项目工作遵循本标准。如果两份文档存在冲突，以章程为准。

文档符合性：生命周期文档必须遵循 [Daoji 文档标准](DOCUMENTATION_STANDARD.md)。

## 目的

本标准定义软件变更如何从源请求推进到已验收的软件及留存的验证证据。它定义生命周期阶段、文档裁剪决策、必需的引用、验证工作和退出条件。

本标准适用于规划、实施、审查或验证 Daoji 变更的人员、智能体和工具。章程定义项目原则和工程资产模型。本标准定义操作工作流。

## 工作流入口

用户提示、议题、对话或其他请求可以启动生命周期。原始请求是输入证据，而非权威项目文档。在项目规划实施之前，项目必须将请求转化为可审查的意图和需求。如果可以安全存储来源，项目必须保留使源请求可追溯的链接或引文。项目必须不将推断出的细节视为用户决策。

变更开始时，项目必须创建或确定一个作为工作导航点的变更条目。该条目可以是一份小型变更文档，也可以是仓库中的另一项权威工程资产。它必须链接到适用的生命周期资产，记录其状态，并记录合并或省略单独文档的每项决策。外部议题可以作为输入来源或导航辅助，但不能成为控制性决策的唯一记录。

变更条目支持渐进式披露。人员或智能体从变更条目开始，只访问当前阶段或任务所需的链接。

## 必需的生命周期资产

每项软件变更都必须生成或链接到以下最小文档集：

1. 陈述目标和必需行为的意图与需求。
2. 陈述项目如何执行变更的设计与实施计划。
3. 控制实施工作的适用工程政策。
4. 陈述项目如何测试和验证变更的验证计划。
5. 陈述项目如何实施变更的实施记录。
6. 包含测试和验证结果的验证记录。
7. 列出变更且适合用作拉取请求说明的变更摘要。

当变更链接到适用内容时，现有权威文档可以满足其中一项。小型变更可以将多项内容合并到一份简短的变更文档中，但每个必需章节都必须保持明确。合并资产不会取消必需的信息、审查、验收、可追溯性或退出条件。变更条目必须明确每个必需章节所在的位置。

实施开始前，项目必须验收意图、需求、设计、实施计划、验证计划，以及适用于该工作的任何新增或已变更工程政策。在项目验收或合并已实施的变更之前，必须完成实施记录、验证记录和变更摘要。

对于探索性原型，已验收的原型计划可以满足设计、实施计划和验证计划的要求。原型计划必须陈述临时设计约束、任务和验证标准。它还必须满足章程中的原型生命周期及采纳规则。

## 生命周期阶段与退出条件

### 意图

意图文档陈述预期结果、理由、受影响的人员和群体、约束及成功度量。文档可以包含不完整的信息，但必须标明每项已知的不确定性。

项目必须从源请求推导意图，不得添加未声明的范围。意图必须区分请求的结果与提议的解决方案。当请求存在歧义时，项目必须记录问题，并在验收依赖这些决策的需求之前获得所需决策。如果意图和需求仍保持明确区分，可以将其作为同一文档中的不同章节。

退出条件：文档明确预期结果以及具备所需决策职责的人员。文档链接到源请求，或记录无法保留来源的原因。

### 需求

需求定义可观察的能力、质量、约束和验收标准。在设计阶段之前，需求必须不选择具体实现。

验收意图后，项目必须对其进行分析，以确定功能行为、质量属性、约束、受影响的用户和系统、范围外行为、假设及验收标准。项目必须将缺失信息记录为未解决问题，而不是选择一种便于处理的解释。示例可以阐明需求，但不能替代规范性需求或其验收标准。

退出条件：每项需求都有唯一标识符，并链接到意图文档。每项需求均可测试，或已定义由人员审查的标准。

### 设计

设计定义系统边界、职责、接口、数据模型、故障行为、安全假设和重要选择。设计必须陈述每项重要选择的优点和缺点。项目应该保留重要决策及被否决替代方案的记录。

设计细节必须随风险和未解决问题的增加而增加。单独的设计文档必须陈述背景、目标、非目标、提议的设计、重要优缺点、考虑过的替代方案和未解决问题。当某个主题适用时，设计必须涵盖安全、隐私、可靠性、监控与诊断、无障碍、国际化与本地化、迁移、部署及运维。

在验收实施计划之前，项目必须执行并记录设计评估。变更条目记录初始评估结果。评估必须确定变更是否需要单独的设计文档。当变更有以下一种或多种情形时，必须提供单独的设计文档：

- 引入或变更架构、组件职责、公共接口、持久化数据、模式或跨组件行为。
- 作出重要的技术或依赖项选择。
- 变更安全或隐私边界、信任模型、可靠性目标、兼容性承诺、迁移程序、部署模型或操作程序。
- 具有必须由审查者评估的重大成本、风险、不可逆性、不确定性或替代方案。
- 建立预期后续变更将遵循的模式。

不符合这些条件的局部低风险变更可以在没有单独设计文档的情况下推进。在这种情况下，实施计划必须包含一个**设计评估**章节。该章节必须解释为何无需单独文档，描述实施方式，并链接到该变更所维持的现有设计。该章节即为此项变更的设计记录。缺少单独的设计文档绝不意味着允许智能体在实施期间作出未记录的设计决策。

退出条件：设计涵盖已验收需求，并陈述已知风险和未解决决策。设计评估记录并论证设计应采用单独文档还是实施计划中的章节。

### 工程政策

政策定义适用于多个智能体任务的规则。政策可以定义编码、依赖项、兼容性、测试、安全、系统监控、文档和发布实践的规则。

对于每项变更，项目必须创建政策适用性与完整性评估。评估必须至少检查编码、静态分析、依赖项与软件供应链、接口与兼容性、测试、安全、隐私、数据处理、可靠性与性能、可观测性、文档、无障碍、国际化、迁移、部署、运维和发布。它必须确定：

- 适用于变更的已验收政策。
- 检查每项适用规则的人员或工具。
- 不适用的类别及其原因。
- 适用但没有充分的已验收政策的类别。
- 必需的政策变更、例外、负责人和批准。

当适用政策缺失或不充分时，项目必须在依赖该政策的实施开始前创建或更新并验收该政策。项目必须不将可复用的工程规则隐藏在提示或单个实施任务中。如果项目尚无法定义规则，则依赖该规则的实施必须不开始。例外可以针对特定变更修改已验收政策，但例外不能替代缺失的适用政策。

退出条件：项目确定适用的政策。每项政策均陈述由工具还是人员检查合规性。项目记录每项例外的理由和所需批准。完整性评估表明每个适用类别均有充分的已验收政策，并且该政策的每项例外均获得所需批准。

### 实施计划

实施计划将设计划分为有序且范围明确的智能体任务。每项任务陈述其依赖关系、受影响组件、所需上下文、预期工程资产和验证步骤。每项任务还必须陈述链接到适用需求验收标准的完成标准。

实施计划必须链接到设计评估以及政策适用性与完整性评估。它必须安排作为先决条件的文档、政策、模式、迁移、代码、测试和运维工作的顺序。它必须明确哪些任务必须由人员执行或批准，以及哪些任务可以由智能体或工具执行。

每项智能体任务必须在其实施说明旁设置一个**引用**章节。该章节必须提供最低限度的充分上下文，并尽可能使用具体的文档章节或资产标识符。适用时，它必须包括：

- 授权该任务的意图、需求、验收标准和设计决策。
- 约束该任务的工程政策和已批准例外。
- 相关接口、模式、组件文档、源代码位置和依赖项记录。
- 决定任务是否完成的验证计划条目、现有测试、测试数据规则、工具配置和命令。
- 受该任务影响的迁移、部署、运维、监控、安全和回滚文档。

引用必须按从任务特定材料到更广泛项目材料的顺序排列。任务应该链接到相关章节，而不是复制整份文档。任务必须陈述发现何种情况时要求智能体访问额外引用，或停止并请求决策。此结构使智能体能够渐进式披露上下文，同时不丢失权威约束。

退出条件：计划可行，并链接到要求执行该工作的权威文档。计划明确相关风险，并为智能体提供足够信息，使其无需作出未记录的架构或政策决策即可执行工作。每项任务都有完成标准以及置于任务旁、对其范围而言充分的引用。

### 验证计划

验证计划定义项目如何测试和验证提议的变更。计划必须将每种测试或审查方法链接到适用的需求和验收标准。它必须明确测试类型、命令、环境、所需输入、预期结果，以及执行验证的人员或工具。

计划必须定义所需的验证层级及其执行顺序。计划必须考虑文档与元数据验证、格式化、代码检查、类型检查、其他静态分析、依赖项与许可证检查、安全扫描、单元测试、集成测试、系统或端到端测试、构建与打包检查、迁移测试、性能或可靠性测试，以及人员审查。适用的工程政策决定确切的检查和通过阈值。计划必须对省略通常适用于受影响软件的每个层级给出理由。

计划必须区分实施任务为获得快速本地反馈而运行的检查与项目在合并变更上运行的检查。在测试数据、机密信息、外部服务、非确定性、重试和清理适用时，计划必须定义项目如何控制这些方面。它还必须陈述项目保留哪些证据，以及何种结果要求返回到更早的生命周期阶段。

退出条件：验证计划覆盖每项适用的验收标准，并包含足够信息供人员或工具执行验证。计划覆盖适用的政策检查，并对省略的验证层级给出理由。

### AI 生成的代码

智能体根据已验收的实施计划执行智能体任务。每个智能体的环境都有明确的权限和限制。变更必须保持在范围内并遵循适用政策。智能体必须报告表明早期阶段假设不正确的信息。

退出条件：智能体已生成指定变更，本地检查通过，并且工作结果记录了所有偏差和未解决问题。

### 实施记录

实施记录描述已实施的结果。它必须明确已变更的组件和行为。适用时，它还必须明确接口、数据、模式、配置、依赖项、构建逻辑、部署、迁移和运维方面的变更。它必须记录相对于已验收设计或实施计划的偏差，并链接到受影响的源文件。

退出条件：实施记录描述已集成的变更，并记录每个已知偏差和未解决的实施问题。

### 构建与验证

项目在合并的软件变更上运行其定义的构建、静态分析、测试、安全检查和验收程序。每条证据记录都必须链接到其所验证的需求和智能体任务。

除非适用政策或验证计划要求不同的顺序，否则项目按照从更快、更窄的检查到更广泛检查的顺序执行验证：

1. 验证已变更文档、元数据、标识符、链接和生成文件的一致性。
2. 运行格式化、代码检查、类型检查和其他必需的静态分析。
3. 运行依赖项、许可证、机密信息和安全检查。
4. 运行受影响的单元测试。
5. 运行受影响的集成测试。
6. 运行必需的系统、端到端、迁移、性能、可靠性、构建、打包和验收检查。
7. 由人员或独立工具执行所需审查。

失败必须保持可见。项目必须不以范围更窄的成功检查替代失败的强制检查。当证据推翻早期假设时，项目必须返回需求、设计、政策、规划或实施阶段。

退出条件：项目完成每项能够运行的计划检查，保留结果和失败，并明确每项无法运行的检查。失败、未完成或省略的强制检查必须保持未解决状态，除非具有所需决策职责的人员依据已验收政策明确批准例外。

### 验证记录

验证记录包含来自测试和验证的实际证据。它必须包含命令、环境、输入、预期结果、实际结果、通过或失败状态、失败情况和已批准例外。它必须将每项结果链接到适用的需求、验收标准、验证计划条目和智能体任务。

验证记录是该变更的测试结论文档。它必须包含总体结论，并采用以下结果之一：通过、失败、附带已批准例外的通过，或无法得出结论。结论必须概述需求与政策的覆盖情况、失败或省略的检查、已批准例外、残余风险、不可重复的证据和必需的后续工作。原始日志可以作为单独证据，但结论必须链接到这些日志，并且无需阅读每份日志也能理解。

项目必须不验收或合并结论为失败或无法得出结论的变更。只有当每项例外均满足适用政策和批准规则时，附带已批准例外的通过才有资格获得验收。

退出条件：验证记录包含足够信息，供人员或工具评估每项验收标准并复现每项可重复检查。其总体结论有已记录结果的支持，且没有隐藏任何失败或遗漏。

### 变更摘要

变更摘要提供对提议软件变更的简要描述。它必须适合直接用作拉取请求（PR）说明，无需重写内容。它必须包含以下章节：

- **目的：** 变更的理由和预期结果。
- **相关需求：** 链接到要求或允许该变更的意图、需求、设计决策、实施计划和验证计划。
- **变更：** 受影响的软件资产或组件，以及新增、变更或移除的行为列表。
- **实施说明：** 重要实施细节，以及相对于已验收设计或实施计划的偏差。
- **验证：** 验证方法、命令和结果，以及指向验证记录的链接。
- **风险与兼容性：** 已知风险，以及对兼容性、安全、隐私、迁移、部署和运维的影响。
- **文档：** 该变更新增或更新的文档。
- **未解决工作：** 已知限制、未解决问题和后续工作。

项目必须根据变更的权威工程资产生成或更新变更摘要。PR 说明中的副本不是权威项目文档。如果变更或其验证结果发生变化，项目必须更新权威变更摘要和 PR 说明。

退出条件：变更摘要与实施记录和验证记录一致，并已可用于 PR 说明。

### 可运行软件

最终软件可以在其指定环境中运行。记录必须将软件链接到其源代码、文档、构建输入和验证证据。

退出条件：软件满足发布或部署标准，且交付的行为链接到已验收的意图文档。

## 变更流程

对于每项提议的软件变更，项目必须执行以下流程：

1. 捕获源请求并创建或确定变更条目。
2. 确定受影响的权威文档和当前软件行为。
3. 推导或更新意图。记录不确定性，并针对缺失的每项必需意图决策向人员询问。
4. 验收意图。
5. 推导或更新需求和验收标准。解决或记录缺失的需求决策，然后验收需求。
6. 在变更条目中记录初始设计评估结果。当评估要求时，创建单独的设计文档。否则，在实施计划中预留设计评估和实施方式章节。
7. 评估工程政策的适用性与完整性。在依赖相关政策的工作开始前，创建或更新适用政策并记录已批准例外。
8. 创建实施计划。定义有序的智能体任务、完成标准，以及置于每项任务附近并渐进式披露的引用。
9. 创建验证计划。将验收标准和适用政策规则映射到静态检查、测试、审查、证据和通过阈值。
10. 确定实施前资产是否包含所有必需信息、相互一致并满足各自的退出条件。
11. 在实施开始前验收设计、实施计划、验证计划以及新增或已变更的工程政策。
12. 将实施和测试任务分配给人员、智能体或工具。收集结构化工作结果，并在任务需要未记录的设计或政策决策时停止。
13. 创建或更新实施记录。
14. 在合并的变更上运行计划的政策检查、静态分析、单元测试、集成测试、更广泛的测试、构建和审查。
15. 创建验证记录和测试结论。将证据链接到适用的验收标准、政策、验证计划条目和智能体任务。
16. 创建或更新变更摘要。
17. 根据已记录的结论和批准规则拒绝、修订或验收变更。
18. 将更新后的权威文档和留存证据存储在版本控制中。

Daoji 必须在适用的自开发级别支持此流程或实现其自动化。如果当前 Daoji 级别不支持某个步骤，则必须由人员和通用工具执行该步骤。

当新信息表明某项假设不正确时，流程必须允许返回到更早阶段。

## 当前工程政策缺口

章程中的初始政策并未构成完整的实施政策集。项目尚未针对以下主题验收具体政策：

- 源代码风格、格式化、代码检查、类型检查、静态分析、代码审查和生成代码。
- 依赖项选择、版本锁定、更新、漏洞响应、许可证、来源和软件供应链控制。
- 接口、数据格式和模式的兼容性、版本控制及弃用。
- 测试层级、覆盖率预期、隔离、测试数据、非确定性和通过阈值。
- 身份验证、授权、威胁建模、敏感信息日志记录，以及初始机密信息访问规则之外的安全事件响应。
- 隐私、数据分类、保留、删除和区域限制。
- 可靠性目标、性能、容量、监控、日志记录、追踪、告警、诊断、备份和恢复。
- 无障碍、国际化、本地化、迁移、部署、运维、发布、回滚和制品完整性。

此列表是已知政策缺口记录，而不是一组隐含政策。在首次实施选择某项技术或影响上述任一主题之前，项目必须定义并验收适用政策。
