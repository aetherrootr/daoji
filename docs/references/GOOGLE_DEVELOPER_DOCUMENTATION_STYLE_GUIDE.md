# Google developer documentation style guide: Daoji profile

Status: Adopted

Document type: Editorial standard profile

Source review date: 2026-07-27

## Purpose

This document is the repository copy of the Google writing guidance that Daoji
adopts. Authors and reviewers must use this file instead of treating the
current Google website as a project requirement.

This file records the guidance that applies to Daoji. It is not a complete
copy of the Google Developer Documentation Style Guide. Google-specific product
rules do not apply to Daoji unless an accepted project document adopts them.

## Rule priority

The Daoji project charter defines the priority of writing rules. If this

authors and reviewers must follow the higher-priority project document.

## Global audience

- Use US English.
- Use simple and precise words.
- Use short sentences.
- Use one term for one concept.
- Define project-specific terms and unfamiliar abbreviations.
- Avoid idioms, slang, humor, metaphors, and culture-specific references.
- Write text that preserves its meaning during machine translation.
- Repeat a noun or helper word when the repetition prevents ambiguity.
- Do not assume that a reader is a native English speaker.

## Sentence structure

- Use subject-verb-object word order when possible.
- Keep the subject and verb near the start of the sentence.
- Put a condition before the instruction that depends on the condition.
- Prefer one primary requirement or idea in each sentence.
- Avoid long groups of nouns that modify another noun.
- Avoid phrasal verbs when a single, common verb has the same meaning.
- Include relative pronouns such as `that` and `which` when they prevent
  ambiguity.

## Voice and tense

- Prefer active voice.
- Identify the person, agent, tool, or system that performs an action.
- Use present tense for general behavior.
- Use future tense only for an event that occurs in the future.
- Do not use future tense to describe an unaccepted product capability.
- Use a direct, respectful, and professional tone.
- Avoid language that is excessively formal, casual, promotional, or playful.

## Titles and headings

- Use sentence case.
- Use one level-1 heading in each document.
- Use a noun phrase for a conceptual heading.
- Start a task heading with a base-form verb.
- Use a logical heading hierarchy, and do not skip heading levels.
- Do not use section numbers only to show document order.
- Keep punctuation simple.
- Do not put links in headings.
- Add introductory text between a parent heading and its child headings.

## Lists

- Introduce a list with a complete sentence when the heading does not provide
  enough context.
- Use a numbered list when order is important.
- Use a bulleted list when order is not important.
- Use parallel grammar, capitalization, and punctuation.
- Start each item with a capital letter.
- End a complete sentence with a period.
- Do not add a period to a short item that has no verb.
- Use a serial comma in a list within a sentence.

## Links and formatting

- Use link text that describes the destination.
- Do not use vague link text such as `click here`.
- Use code formatting for file paths, commands, code elements, and literal
  values.
- Use the same formatting for the same type of content.
- Do not use an image or diagram as the only source of required information.

## Accessibility and inclusion

- Use inclusive language.
- Avoid language that insults, excludes, or stereotypes people.
- Do not describe a task as easy or simple for the reader.
- Provide text for information that appears in an image.
- Avoid directional references such as `above` and `below` when a stable name or
  link can identify the content.

## Planned features

- Clearly distinguish current behavior from planned behavior.
- Do not describe an unaccepted planned feature as available.
- Store detailed plans in accepted planning documents.
- Use present-tense requirements in planning documents when possible.

## Exceptions

Clarity and consistency for the intended audience take priority over mechanical
compliance. The project must record the reason for each deliberate exception to
an applicable rule.
